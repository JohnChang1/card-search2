# 📋 程序弱点报告 SKILL

## 概述
这份SKILL提供了一套标准化的程序弱点报告流程，用于系统性地识别、分类和跟踪代码中的潜在问题。

---

## 1️⃣ 弱点分类系统

### 1.1 严重性等级
| 等级 | 标记 | 说明 | 示例 |
|------|------|------|------|
| 🔴 严重 | CRITICAL | 影响系统正常运行，可能导致崩溃或数据丢失 | 数组越界、内存泄漏、SQL注入 |
| 🟠 高 | HIGH | 功能异常或性能显著下降，用户体验受影响 | 无限循环、未处理异常、XSS漏洞 |
| 🟡 中 | MEDIUM | 可能导致功能缺陷或安全隐患，但影响有限 | 硬编码密钥、缺少输入验证、废弃代码 |
| 🔵 低 | LOW | 代码质量问题，不影响功能，但需要改进 | 未使用的变量、冗余代码、注释不清 |

### 1.2 弱点类型
- **🐛 BUG** - 逻辑错误或功能异常
- **⚡ PERFORMANCE** - 性能瓶颈或优化机会
- **🔐 SECURITY** - 安全漏洞或风险
- **♻️ CODE_QUALITY** - 代码风格或可维护性问题
- **📚 DOCUMENTATION** - 文档缺失或不准确
- **⚙️ ARCHITECTURE** - 架构设计问题

## 2️⃣ 弱点检查清单

### 代码结构检查
- [ ] 是否有冗余或重复的代码块（函数、逻辑）
- [ ] 是否有已弃用或注释掉的代码
- [ ] 函数/模块职责是否单一清晰
- [ ] 代码层级结构是否合理

### 功能与逻辑检查
- [ ] 是否处理了所有边界情况（空值、极值）
- [ ] 循环是否可能无限循环或过度迭代
- [ ] 条件判断逻辑是否正确完整
- [ ] 是否有未处理的异常或错误情况

### 性能检查
- [ ] 是否有不必要的全局变量声明
- [ ] API调用是否过度频繁（可优化缓存）
- [ ] 是否有阻塞操作（同步调用）可改为异步
- [ ] DOM操作是否频繁（可批量处理）
- [ ] 算法时间复杂度是否可优化

### 安全性检查
- [ ] 是否有硬编码的敏感信息（密钥、密码、API地址）
- [ ] 用户输入是否都经过验证/清理
- [ ] 是否有XSS漏洞（未转义的HTML）
- [ ] 是否有SQL注入风险
- [ ] API通信是否使用HTTPS

### 可维护性检查
- [ ] 变量/函数名是否清晰有意义
- [ ] 复杂逻辑是否有注释说明
- [ ] 是否有错误处理的完整说明
- [ ] 代码是否遵循项目的编码规范

## 4️⃣ 实际应用示例

### 示例1: 废弃代码问题
```
【弱点ID】WK-20260419-001
【严重性】🟡
【类型】CODE_QUALITY

【文件位置】
路径: src/js/script.js
行号: L180-L270

【问题描述】
存在已废弃的备用函数 fetchData2()，占用约90行代码，功能已被主函数 fetchData() 替代。

【影响分析】
- 直接影响: 增加代码维护成本，易造成困惑
- 间接影响: 如果修改逻辑，需要同时维护两个版本
- 用户影响: 无直接用户影响

【根本原因】
在代码重构过程中，保留了备用方案但未清理。

【修复建议】
删除 fetchData2() 函数及其相关注释，确保单一实现路径。

【验证方法】
- [ ] 确认 fetchData() 包含所有必要功能
- [ ] 运行测试确保搜索功能正常
- [ ] 验证无其他地方调用 fetchData2()

【优先级】
- 修复优先级: ⭐⭐ (低优先级，不影响功能)
- 预计工作量: 低
```

### 示例2: 性能问题
```
【弱点ID】WK-20260419-002
【严重性】🟠
【类型】PERFORMANCE

【文件位置】
路径: src/js/script.js
行号: L88-L130

【问题描述】
fetchData() 函数每次API调用后，对完整列表进行全量过滤，在结果集较大时会有明显延迟。

【影响分析】
- 直接影响: 搜索反应时间长，用户体验不佳
- 间接影响: 频繁调用可能导致浏览器卡顿
- 用户影响: 高 - 直接影响核心功能性能

【根本原因】
过滤逻辑在API层而非查询层，导致客户端需要处理大量数据。

【修复建议】
优化API查询参数或在服务器端进行过滤，减少客户端处理量。

【验证方法】
- [ ] 使用Chrome DevTools Timeline测量优化前后性能差异
- [ ] 在大结果集（500+条）上测试响应时间
- [ ] 确保过滤结果准确无误

【优先级】
- 修复优先级: ⭐⭐⭐ (中高优先级)
- 预计工作量: 中
```

## 5️⃣ 检查清单执行流程

### 📌 每次代码审查的步骤

1. **初始扫描** (5分钟)
   - 阅读代码整体结构
   - 识别明显的问题区域
   - 标记需要深入检查的部分

2. **详细检查** (15分钟)
   - 逐个应用 **2.2 弱点检查清单** 的各项
   - 记录所有发现的问题
   - 评估严重性和影响范围

3. **分类归档** (5分钟)
   - 为每个弱点分配ID和严重性
   - 按类型分组组织
   - 确定修复优先级

4. **报告生成** (10分钟)
   - 使用 **3.1 弱点报告模板** 格式化输出
   - 提供清晰的代码示例和修复建议
   - 记录相关链接和备注

5. **跟踪回顾** (定期)
   - 每周回顾修复进度
   - 更新弱点状态（未开始 → 进行中 → 已修复 → 已验证）
   - 总结经验教训

## 7️⃣ 常见弱点参考库

### JavaScript 常见弱点
- **未声明的全局变量** - 可能污染全局作用域
- **回调地狱/Promise链不当** - 难以维护和调试
- **闭包陷阱** - 内存泄漏或变量捕获错误
- **类型强制转换问题** - `==` vs `===` 的混用
- **异步操作未正确处理** - 竞态条件或超时

### DOM 操作常见弱点
- **频繁的DOM查询** - 应该缓存选择器结果
- **直接修改innerHTML** - 存在XSS风险，应用textContent或安全转义
- **事件监听器未移除** - 导致内存泄漏
- **批量DOM更新** - 应该使用DocumentFragment或离屏渲染

### 数据处理常见弱点
- **硬编码的配置值** - 应该外部化到配置文件
- **缺少输入验证** - 应该验证所有外部数据
- **错误处理不完整** - 应该有 try-catch 和错误日志
- **数据格式假设不明确** - 应该有类型检查或schema验证
